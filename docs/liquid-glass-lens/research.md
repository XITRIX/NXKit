# Native liquid-lens reference

The reference is the running UIKit implementation on **iPadOS 27.0, build
24A434**, rendered at 2×. It is not a reconstruction of Apple's private source.
The lens is a separate selected-item surface; treating it as another regular
frosted-glass button misses its content replacement and lift behavior.

## Sources and reuse boundary

Apple documents the public controls and their state, not a public lens class:
[UITabBar](https://developer.apple.com/documentation/uikit/uitabbar),
[UISwitch](https://developer.apple.com/documentation/uikit/uiswitch), and
[UISlider](https://developer.apple.com/documentation/uikit/uislider).

The primary source for identifying callable selectors was Telegram's
[LiquidLensView.swift at commit 6ad963e5b62d354da79040f388ae2b9132fb17b8](https://github.com/TelegramMessenger/Telegram-iOS/blob/6ad963e5b62d354da79040f388ae2b9132fb17b8/submodules/TelegramUI/Components/LiquidLens/Sources/LiquidLensView.swift)
(Git blob `9ab506f84621e3faf650133ef6911799d636f4e6`). Its setup distinguishes
normal content, selected content, a resting view, and a lifted container. It also
contains application-specific filtering, dimensions, and motion choices. Those
are not stock UIKit behavior, and its implementation was not copied here.

[Livsy Code's manual-construction article](https://livsycode.com/swiftui/exploring-_uiliquidlensview/)
provides a second pointer to that interface. Scalar types in examples are not an
ABI authority: runtime method encodings below determine the fixture's types.

[LiquidGlassKit](https://github.com/DnV1eX/LiquidGlassKit) and its
[LiquidLensView.swift](https://github.com/DnV1eX/LiquidGlassKit/blob/master/Sources/LiquidGlassKit/LiquidLensView.swift)
were inspected as independent experiments. A copying license was not established
in the inspected root; none of that implementation was copied. Its custom
implementation is not an oracle for Apple's rendering or animation constants.
[Livsy90/LiquidLens](https://github.com/Livsy90/LiquidLens) is another primary
manual-construction experiment, with an [MIT license](https://github.com/Livsy90/LiquidLens/blob/main/LICENSE.md).
It documents the same private selector family, selected/punchout content, and
rest/lift transitions. No code from it was copied. Runtime evidence below,
not a third-party implementation, defines this comparison.

The native fixture is independently written Objective-C that invokes observed
selectors. Private calls are confined to `Demo/GlassComparison/LensReference.m`;
they are not linked into the portable library. Any NXKit lens API is an NXKit
extension, not a claim that Apple exposes a public `UILensView` API.

## What the runtime establishes

`_UILiquidLensView` exists and inherits from `UIView`. The alternative names
`_UILensView` and `_UIFluidLensView` were absent in this runtime. That is a
bounded observation about this OS build.

| Selector | Observed ABI / role |
| --- | --- |
| `initWithRestingBackground:` | `@24@0:8@16`; caller supplies a `UIView` |
| `setLiftedContainerView:` | View containing the backdrop and content to lift |
| `setLiftedContentView:` | Separate selected-content view |
| `setOverridePunchoutView:` | Normal-content view that is cut out beneath the selection |
| `setLiftedContentMode:` | `v24@0:8q16`; signed 64-bit `NSInteger` here |
| `setStyle:` | `v24@0:8q16`; signed 64-bit `NSInteger` here |
| `setWarpsContentBelow:` | `v20@0:8B16`; Boolean |
| `setRestingBackgroundColor:` | Color property, not a replacement for the supplied resting view |
| `setLifted:animated:alongsideAnimations:completion:` | `v40@0:8B16B20@?24@?32`; two Booleans and two blocks |

The last column describes how these properties participate in the observed
fixture; private API semantics may change between OS releases.

The native controls use distinct configurations:

| Control | Resting lens size | Style / content mode | Warps content below | Spec class |
| --- | --- | --- | --- | --- |
| `UITabBar` | 84×36 Home; 99.5×36 Favorites; 94×36 Settings | 1 / 1 | Yes | `UIKit._UILiquidLensViewLargeVariantSpec` |
| `UISwitch` | 37×24 | 0 / 0 | Yes | `UIKit._UILiquidLensViewSmallVariantSpec` |
| `UISlider` | 37×24 | 0 / 0 | No | `UIKit._UILiquidLensViewSmallVariantSpec` |

These observations do **not** establish an 80×80 automatic threshold. In the
manual fixture, explicitly choosing style 1 produces the large spec even for a
48×48 view; style 0 produces the small spec even for a 124×64 view. Control
configuration and geometry need separate tests.

## Resting content and appearance

The real tab bar has sibling selected content, lens, normal content, and a
destination-out view. The selected content is blue at rest. Its initializer
receives a private `_UITabSelectionView` as the resting view. Switch and slider
receive an ordinary view and report an opaque white resting-background color.

The independent manual fixture uses duplicate icon/title rows. The normal row
uses `labelColor`; the selected row uses sRGB `(0, 122/255, 1)`. Both rows retain
the same full-container coordinates while the lens moves over them. This makes
selection a spatial replacement of content, not a tint applied to the whole bar.

Two setup experiments isolate the caller's responsibilities:

- An empty clear resting view creates no visible resting pill, even after
  setting `restingBackgroundColor` to black at 0.1 alpha.
- Giving that resting view a black 0.1-alpha background and capsule corners
  creates a visible pill. A lens layer at z-position 10, above the base-glass
  container at z-position 1, also makes selected content visible at rest.
  Without that ordering, normal content was punched out but selected Home was
  missing in this fixture.

Thus a portable implementation needs a usable resting appearance and separately
aligned selected content. It cannot assume that setting the private color
property or merely inserting a transparent lens supplies both. The precise
compositor dependency behind the observed ordering remains unproven.

## Lifted appearance and motion

**Later evidence:** [native touch-driven motion](native-motion.md) now records
actual UIKit slider, tab-bar, and switch dragging, reversals, release, and
interruption. The manual center paths described below remain historical
authored-input probes and must not be used as native gesture physics.

The lifted manual lens visibly refracts sharp background lines and colored
stripes. It has a clear, prismatic surface and contact shading rather than the
regular bar's frosted material. Its hierarchy includes a `CABackdropLayer`,
private `ClearGlassView`, SDF elements backed by `CASDFElementLayer`, and portal
views. Class names establish composition, not the underlying shader equation.

The fixture's transition calls the native lifted-state API, but the **caller**
supplies bounds growth of four points on each side and a cosine-eased center
path. Those values must not be reported as measured UIKit inflation, drag
damping, or snap dynamics. Per-frame hierarchy and presentation transforms are
retained so the native response to that declared input can be inspected.

The public tab bar, switch, and slider are included as independent resting
controls. Programmatically changing selected item, on state, and value observes
their resulting states; it does not measure their touch-driven trajectories.

There is nevertheless an observable native response to the authored motion:
the fixture never assigns a lens transform, but its presentation layer stretches
and translates. For the light-theme center-to-right input, 156 sampled frames
span horizontal scale 0.855–1.120, vertical scale 0.843–1.146, and horizontal
translation −8.35–7.70 points. It returns to identity by about 1.7 seconds after
the initial lift. The opposite direction has different extrema. The
[four transform traces](native/motion-dark0-to2.csv) preserve this evidence; these
are examples under the declared timing, not universal damping parameters.

## Reproduce the native reference

The fixture uses a centered 720×560-point stage. Its manual base is
`(40,250,640,76)` with capsule corners. A 116×56-point lens is centered in one of
three equally spaced columns. Separate samples are 48×48, 80×80, and 120×64 at
centers `(120,425)`, `(360,425)`, and `(600,425)`.

```sh
python3 Demo/GlassComparison/build-lens.py /private/tmp/nxkit-lens-native
python3 Demo/GlassComparison/capture-lens.py DEVICE_UDID /private/tmp/nxkit-lens-native
```

Use Python with Pillow and NumPy, Xcode, and a compatible booted simulator.
The build targets the simulator only. The capture driver installs and launches
only `org.nxkit.LensReference`, then sends requests through that app's Documents
directory. A third argument can provide a JSON array of cases.

The default [52-case matrix](../../Demo/GlassComparison/lens-cases.json) includes
both themes; gray, line, colored-stripe, and RGB backgrounds; resting/lifted
states; selection endpoints; style 0/1; two additional sizes; and center-motion
inputs in both directions. Custom requests support selected index,
size, style, backdrop warping, and a declared center-motion path. Every capture
includes raw framebuffer, cropped sRGB image, source/executable hashes, runtime
method encodings, final hierarchy, and per-frame lens metadata. The driver reads
the actual PNG profile and converts it to sRGB; it does not assume that raw
Display P3 bytes are sRGB.

The last two cases also export fresh public UIKit icon/title rows as transparent
1280×152-pixel PNGs. The driver copies these into `native/content/` and preserves
alpha while normalizing the color profile. The saved
[comparison-only assets](native/content/manifest.json) isolate optical differences
from differences in font or icon rasterization. They are not Demo resources.

## Portable implementation evidence

`LensView` is an explicitly named NXKit extension. Its resting background is
clear unless the caller provides content or a color. Selected content is recorded
as a separate retained source, preserving complete source support until the
finished lens is clipped. `setLiftedContentView()` can reference a full source
row outside the lens through a weak reference; passing nullptr returns to the
owned `contentView()`. Its ordinary display is suppressed while the lens owns
that source, avoiding double compositing of antialiased or translucent pixels.
Source and ancestor visibility/opacity still apply. Interior coordinates and
color remain stable; the new perimeter investigation supplies the missing
edge-mapping constraints. Lifted state leaves public geometry alone. A critically damped, frame-rate-independent transition is an
NXKit timing choice; it does not claim the native velocity-dependent response.

For example, a control can create and position its selection lens like this:

```cpp
auto lens = new_shared<LensView>(LensView::Style::selection);
lens->setFrame({12, 10, 116, 56});
lens->setRestingBackgroundColor(UIColor::black.withAlphaComponent(.1f));
auto selectedMark = new_shared<UIView>(NXRect(46, 16, 24, 24));
selectedMark->setBackgroundColor(UIColor::systemBlue);
lens->contentView()->addSubview(selectedMark);
container->addSubview(lens);

// The containing control routes its own press, drag, and release events.
lens->setLifted(true, true);
// Change lens->center()/frame through the ordinary view setters as needed.
lens->setLifted(false, true);
```

Use `Style::regular` for the knob-like variant and `Style::selection` for the
tab-selection variant. The caller supplies the resting view's fill or subviews,
selected content, geometry, and event routing. `restingBackgroundView()` remains
the same owned view across transitions; its own alpha is preserved by an
internal fading host. Ordinary `UIView` bounds animations resize the internal
surfaces, and changes in traits/display scale reach the optical pass. The
portable API intentionally omits private portal views, a backdrop-warp flag
whose independent semantics were not established. The later opt-in elastic
contact path is documented separately in [the native motion evidence](native-motion.md)
and [the response comparison](motion/README.md); it is distinct from this
earlier lift-material transition.

All standalone style-1 lens pixels in the sampled area were identical between
themes for gray, lines, colored stripes, and all three primary-color backdrops.
The base material still changes with the theme. The style-0 controls revealed a
separate body response: gray 128 becomes 141; red becomes `(255,20,20)`; green
becomes `(7,255,7)`; blue becomes `(24,24,255)`. These independent uniform controls
fit a generic additive achromatic term `0.1 * (1 - Rec.709 luma)` followed by
clamping, with rounding to bytes. The colored-stripe center independently agrees
with the same term. Style 1 leaves the center color unchanged.

Style 0 retains that same interior tone in dark mode, but its shaded perimeter
becomes stronger. Style 1's standalone pixels were theme invariant in these
captures. The portable implementation therefore adapts the regular lens's edge
shading separately from its body tone.

The [aligned standalone measurements](native/material-metrics.json) cover both
styles, both themes, six backgrounds, and three sizes. Error is the mean absolute
RGB-byte difference in sRGB. The body excludes the outer four points; the edge
region lies between 0.5 and four points inside the capsule. Values average the
six background cases, not arbitrary full-screen pixels.

| Portable variant | Theme | Body error | Edge error |
| --- | --- | ---: | ---: |
| Regular | Light | 2.35 | 10.05 |
| Regular | Dark | 3.29 | 16.02 |
| Selection | Light | 1.58 | 8.28 |
| Selection | Dark | 1.58 | 8.28 |

Uniform RGB backgrounds are closer than the line patterns. For selection glass,
their body error is 0.37–0.39; lines remain at 5.75. The measurements therefore
do not support a claim of pixel equality. The full composed bar, text, and
touch-driven behavior require separate comparisons.

Several alternatives were rejected. Narrow inward displacement bent the lines
in the wrong direction for the selection lens. A stronger generic RGB sampling
offset increased line and stripe error. A reflected edge sample improved the
regular variant's folded-line appearance while preserving uniform backgrounds;
the selection variant uses a smaller contribution. Drawing contact shading
before the optical pass caused the lens to sample its own exterior contour and
produce a second dark ring, so contact shading is drawn afterward. None of these
experiments recovers Apple's private transfer function.

The private renderer's exact refraction, spectral perimeter, and shadows remain
unknown. The portable optical transfer is a measured approximation and remains
visibly different around native caustics. A small image error is not evidence
for a recovered private equation.

### Centered selected-content evidence and its limitation

The original eight-case centered-star comparison remains saved in
[native/content-order-metrics.json](native/content-order-metrics.json). It showed
that native main ink retains its source coordinates: the native star's opaque
ink was 94.4% byte-exact in one lifted scene, and moving NXKit's main selected
ink above the backdrop lowered mean composed-body error from 6.10 to 1.96/255.
The resting case stayed unchanged. These are valid measurements of that
centered glyph and its main silhouette, not a full lens composition model.

**The perimeter probes supersede the earlier sharp-overlay interpretation.**
They show selected-content grid, text, and colors being strongly refracted at
all four edges while central ink remains sharp. A source clipped to the lens
before distortion, or an unwarped overlay alone, cannot reproduce those cases.
The old centered-star test did not excite these branches and therefore could
not validate their absence. Its slight rim regression (9.26 to 9.49/255) must
not be treated as negligible evidence of general parity.

The new [edge-refraction investigation](edge-refraction.md) separates the main
ink, additional edge branches, backdrop/base optics, and source visibility.
It records observations independently from the portable approximation and
keeps the earlier captures intact.

## Limits

The oracle is iPadOS 27.0, not the user's 27.2 device. The current manual base is
public regular glass, while a real tab bar may configure its backdrop privately.
The manual selected color and resting fill are declared fixture inputs, not
extracted Apple constants. Touch drag elasticity, velocity-dependent stretching,
automatic variant selection, cancellation, accessibility settings, and private
renderer equations remain unestablished by these static captures. Matching a
subset of pixels does not establish general behavioral parity.
